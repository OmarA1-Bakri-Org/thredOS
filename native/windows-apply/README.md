# Windows apply primitive

This is a Windows-only Node-API adapter for the Milestone 2 merge/apply service. It is **not** an apply service or an approval boundary. The canonical project must remain unchanged until the service has verified a current three-input merge plan, exact approval, path scope, content hashes, staged bytes, rollback journal, and post-apply checks. Do not call this module from API routes, CLI handlers, or agents.

The synchronous interface is in [`index.d.ts`](index.d.ts). `identity(root, relative, directory)` obtains the expected volume/file ID for the root, a regular file, or a directory. `prepare(...)` validates those IDs, rejects reparse points and multiply linked files, and keeps handles open without delete sharing. It accepts local-drive roots and `/`-separated relative components only. `commit(token)` performs one rename or delete on the pinned file handle and consumes the token; `close(token)` releases unused handles. The destination rename is relative to a pinned destination-directory handle, with replacement disabled. There is no Git dependency, shell invocation, or recursive operation.

The service's required sequence for a file replacement is: persist and sync an intent journal; capture and hash a durable rollback **copy**; stage and verify candidate bytes outside the target path; obtain source and destination parent identities; call `prepare` for the existing target and stage; recheck content hashes; rename the target into a unique journal backup; hash that backup again before installing the candidate; rename the stage into the now-empty target; verify installed content and persist each resulting identity and journal state; run post-apply gates; then retain rollback evidence. On a failure, recover from the journal and recheck identities before any reverse mutation. A prepared token must be closed promptly in `finally`; it is process-local and cannot be serialized. This module does not guarantee multi-file atomicity or journal durability.

The no-write sharing mode blocked a previously opened writable memory mapping at `prepare` on this host (Win32 sharing violation), and a separate test shows that a new writable mapping cannot be created after `prepare`. The earlier external mapping was able to write only **after preparation had failed**; it was never pinned by a native token. The merge/apply service still needs a separate rollback copy and content verification after the target moves into the journal, because these tests cover one Windows host and do not prove immutability across every supported file system or driver. The adapter is not yet an end-to-end safe apply implementation.

`CreateFileW` omits `FILE_FLAG_OVERLAPPED`, which Microsoft's synchronous-handle contract says blocks an I/O call until completion. The NT rename path still handles an unexpected `STATUS_PENDING` by waiting for terminal completion while its source handle, `IO_STATUS_BLOCK`, and rename buffer remain alive; it never converts a timeout into a definite failure. This defensive path has an unbounded liveness risk if a provider violates or stalls the synchronous contract. A supervised helper process and recovery protocol are required before exposing this adapter to Desktop apply flows that must remain responsive under a stuck file system.

Node 24.19.0, node-gyp 11.5.0, Windows SDK 10.0.26100.0, and VS 2022 Build Tools compiled the addon. `bun run native:build` builds it; `bun run native:test` runs the real temporary-root tests. The native build skips non-Windows hosts, and test discovery skips all native cases there before requiring the addon. Electron 41.0.3's Node 24.14.0 runtime loaded the same Node-API binary and completed a temporary-root rename/readback. `desktop:build` and `desktop:dist` run the native build first. `bun run desktop:dist --dir --win` produced an unpacked app with the `.node` binary under `resources/app.asar.unpacked/native/windows-apply/build/Release/`. The packaged `thredOS Desktop.exe` loaded `app.asar/native/windows-apply/index.cjs` and completed a temporary-root rename/readback. The packaged binary's hash matched the latest built addon (`11223A6E847AF8B39ED67E091B369A444043689FD80130DB43E5AA608D9AD86F`). This proves packaged loading on this host; it does not close the supported-Windows matrix or the full apply-service acceptance gate.

On this Windows host, `SetFileInformationByHandle(FileRenameInfo)` and `FileRenameInfoEx` with a non-null `FILE_RENAME_INFO.RootDirectory` returned Win32 87, even with a simple destination basename, traversal access, the documented minimum buffer size, and a NUL-extended diagnostic buffer. The same Win32 call with an absolute destination worked, and `NtSetInformationFile(FileRenameInformation)` with the pinned directory handle worked. The addon therefore dynamically resolves the NT user-mode export and fails closed if unavailable; there is no absolute-path fallback. The underlying reason for Win32 87 is not established. This is a portability risk that must be checked on supported Windows versions and in packaged Electron before integration.
